01

Resumen de tu proyecto

🧠
Qué construiste

Un sistema de logging distribuido: varios servicios generan logs falsos y los mandan a un servidor central.

📡
Cómo se comunican

Los clientes hacen requests HTTP al servidor usando POST /logs. El formato del body es JSON.

🔐
Cómo se autentican

Cada servicio usa un token estático en el header Authorization. No estás usando JWT real.

🗄️
Dónde se guardan

El servidor valida los logs y los guarda en SQLite, en el archivo logs.db.

Explicación corta

Mi proyecto simula un entorno con 3 servicios: auth-service, payments-service y socket-service. Cada uno genera logs con timestamp, service, severity y message. Después los envía al servidor central mediante HTTP. El servidor valida el token, valida el formato del log, agrega received_at y guarda todo en una base SQLite. Luego se pueden consultar los logs con GET /logs y filtros por fecha.

02

Arquitectura del sistema

clients/ — servicios simulados

auth_service.py, payments_service.py y socket_service.py generan logs falsos pero realistas. Cada servicio tiene nombre, token y mensajes propios.

base.py — lógica común

Genera timestamps, severities aleatorios y mensajes. También arma la request HTTP con Content-Type y Authorization.

POST /logs — recibir logs

El servidor valida el token, acepta un log o una lista de logs, valida campos obligatorios y guarda los válidos.

GET /logs — consultar logs

Permite leer los logs guardados. Acepta filtros opcionales: timestamp_start, timestamp_end, received_at_start y received_at_end.

logs.db — SQLite

Guarda id, received_at, timestamp, service, severity y message. También tiene índices para acelerar búsquedas por fecha.

Código clave que tenés que conocer

config.py — tokens válidos

VALID_TOKENS = {
    "Token svc-auth-penguin-001":     "auth-service",
    "Token svc-payments-penguin-002": "payments-service",
    "Token svc-socket-penguin-004":   "socket-service",
}

Esto no es JWT. Es una lista manual de tokens estáticos. Si el header Authorization coincide con una clave del diccionario, el servidor acepta la request.

validators.py — autenticación y validación

def authenticate() -> bool:
    return request.headers.get("Authorization", "") in VALID_TOKENS

def validate_log_entry(entry: dict):
    for field in ["timestamp", "service", "severity", "message"]:
        if field not in entry:
            return False, f"Campo faltante: '{field}'"

Primero se verifica quién manda el log. Después se revisa que el log tenga los campos mínimos y que el severity sea válido.

database.py — tabla y filtros

CREATE TABLE IF NOT EXISTS logs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    received_at TEXT    NOT NULL,
    timestamp   TEXT    NOT NULL,
    service     TEXT    NOT NULL,
    severity    TEXT    NOT NULL,
    message     TEXT    NOT NULL
)

La base guarda dos fechas importantes: timestamp es cuándo ocurrió el evento en el servicio, y received_at es cuándo llegó al servidor.

05

Qué tenés que decir en la presentación

Intro de 30 segundos

Este proyecto es un sistema de logging distribuido. Separé el código en clientes y servidor. Los clientes simulan servicios reales que generan logs y los mandan por HTTP. El servidor central los recibe, valida el token, valida el formato, los guarda en SQLite y permite consultarlos con filtros por fecha.

Frases clave para defender decisiones

  • Usé Flask porque el challenge necesitaba endpoints HTTP simples y claros.
  • Usé SQLite porque es suficiente para una demo local y no requiere configurar un servidor de base de datos externo.
  • Separé clients/ y server/ para mostrar arquitectura cliente-servidor.
  • Separé routes/, validators.py y database.py para mantener responsabilidades claras.
  • No uso JWT real; uso tokens estáticos en Authorization porque el challenge pedía autenticación con tokens.
  • received_at lo agrega el servidor para saber cuándo llegó el log, independientemente del timestamp del cliente.
  • El POST acepta batches para no mandar un request por cada log cuando hay muchos.
Respuesta si te preguntan por JWT:
No, no implementé JWT real. Algunos mensajes simulados del auth-service hablan de JWT, pero son solo contenido del log. La autenticación real de mi sistema es con tokens estáticos enviados en el header Authorization.

# Consultar logs
curl -H "Authorization: Token svc-auth-penguin-001" http://localhost:8080/logs

# Enviar un log manualmente
curl -X POST http://localhost:8080/logs \
  -H "Authorization: Token svc-auth-penguin-001" \
  -H "Content-Type: application/json" \
  -d '{"timestamp":"2026-05-03T12:00:00Z","service":"auth-service","severity":"INFO","message":"Demo manual"}'

# Consultar con filtro
curl -H "Authorization: Token svc-auth-penguin-001" \
  "http://localhost:8080/logs?timestamp_start=2026-05-03T00:00:00Z"
