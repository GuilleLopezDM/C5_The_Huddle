01

Conceptos fundamentales

¿Qué es un sistema de logging distribuido?

Es una infraestructura que recolecta, centraliza y almacena registros (logs) generados por múltiples servicios que corren de forma independiente. En vez de que cada servicio guarde sus logs localmente, todos los envían a un servidor central que los unifica.

  • Múltiples servicios generan eventos → los envían por red a un servidor central
  • El servidor valida, procesa y persiste cada log en una base de datos
  • Los logs son consultables con filtros: por fecha, por servicio, por severidad
  • La autenticación garantiza que solo servicios autorizados puedan escribir logs

¿Por qué es importante?

En sistemas con múltiples servicios, rastrear un error sin logs centralizados es como buscar una aguja en 5 pajares distintos, en formatos distintos, sin saber en qué pajar empezar.

  • Observabilidad: sabés qué pasó, cuándo, y en qué servicio
  • Debugging: podés correlacionar eventos de múltiples servicios en el tiempo
  • Auditoría: registro histórico de operaciones para compliance
  • Alertas: podés detectar patrones (muchos ERROR seguidos = algo está mal)

Anatomía de un log

Cada registro debe tener campos estándar para que sea útil y consultable:

// Estructura de un log en este sistema
{
  "timestamp": "2025-04-30T08:23:15.432Z",   // cuándo pasó (ISO 8601)
  "service":   "payment-service",            // quién lo generó
  "severity":  "ERROR",                        // qué tan grave es
  "message":   "Timeout al conectar con DB"   // qué pasó
}

// El servidor agrega received_at (cuándo llegó al servidor)
// Útil cuando el reloj del cliente puede estar desincronizado
  • timestamp: cuándo ocurrió el evento en el servicio de origen
  • service: identificador del servicio que generó el log
  • severity: DEBUG < INFO < WARN < ERROR < FATAL
  • message: descripción legible del evento
  • received_at: timestamp del servidor al recibir (lo agrega el servidor)

Niveles de severidad

La jerarquía determina qué tan urgente es el evento. En producción generalmente se filtran los DEBUG para reducir ruido.

  • DEBUG: información muy detallada, solo útil durante desarrollo
  • INFO: operaciones normales del sistema (usuario logueado, pedido creado)
  • WARN: algo inusual pero el sistema sigue funcionando
  • ERROR: algo falló pero el servicio sigue vivo
  • FATAL: error crítico, el servicio probablemente se va a caer

Token authentication

Cada servicio tiene un token único que lo identifica. El servidor verifica ese token antes de aceptar cualquier log. Si no es válido, rechaza la request con 401.

// El cliente envía el token en el header
Authorization: Token svc_payment_abc123xyz

// El servidor lo extrae y valida contra su lista
const VALID_TOKENS = {
  'svc_payment_abc123xyz': 'payment-service',
  'svc_auth_def456uvw':    'auth-service',
  'svc_notif_ghi789rst':   'notification-service'
}

// Si no está en el mapa → 401 Unauthorized

Filtros por fecha y la diferencia timestamp vs received_at

El sistema maneja dos tipos de timestamp distintos, y es importante entender por qué:

  • timestamp: cuándo pasó el evento en el servicio (reloj del cliente)
  • received_at: cuándo llegó el log al servidor central (reloj del servidor)
  • Un servicio puede estar en otra zona horaria o tener el reloj desincronizado
  • Filtrar por received_at es más confiable para saber "qué llegó hoy"
  • Filtrar por timestamp es mejor para "qué pasó entre las 14:00 y 15:00"
02

Arquitectura del sistema

Servicios simulados (clientes)

Generan logs falsos con datos realistas. Cada uno tiene un token único. Envían POST /logs con JSON. Pueden enviar 1 o N logs a la vez. Manejan errores de red.

Middleware de autenticación

Lee el header Authorization. Valida el token contra la lista. Si es inválido → 401 {"error": "Quién sos, bro?"}. Si es válido → pasa al siguiente handler.

POST /logs — recibir logs

Valida que el body tenga timestamp, service, severity, message. Agrega received_at = now(). Inserta en la base de datos. Soporta array de logs (batch). Responde 201 Created.

GET /logs — consultar logs

Lee query params opcionales: timestamp_start, timestamp_end, received_at_start, received_at_end. Construye el query SQL dinámicamente según los filtros presentes. Devuelve array ordenado por timestamp DESC.

Base de datos

Tabla logs: id (PK autoincrement), timestamp TEXT, service TEXT, severity TEXT, message TEXT, received_at TEXT. Índice en timestamp y received_at para queries eficientes.

Código clave que tenés que conocer

Servidor — estructura principal (Express + SQLite)

const express = require('express');
const Database = require('better-sqlite3');

const app = express();
app.use(express.json());

const db = new Database('logs.db');

// Crear tabla si no existe
db.exec(`
  CREATE TABLE IF NOT EXISTS logs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp   TEXT NOT NULL,
    service     TEXT NOT NULL,
    severity    TEXT NOT NULL,
    message     TEXT NOT NULL,
    received_at TEXT NOT NULL
  );
  CREATE INDEX IF NOT EXISTS idx_timestamp   ON logs(timestamp);
  CREATE INDEX IF NOT EXISTS idx_received_at ON logs(received_at);
`);

// Tokens válidos por servicio
const VALID_TOKENS = {
  'token_payment_001': 'payment-service',
  'token_auth_002':    'auth-service',
  'token_notif_003':   'notification-service'
};

Middleware de autenticación

// Este middleware se ejecuta ANTES de los handlers de rutas
function authMiddleware(req, res, next) {
  const authHeader = req.headers['authorization'];

  // Verificar que el header exista y tenga el formato correcto
  if (!authHeader || !authHeader.startsWith('Token ')) {
    return res.status(401).json({ error: 'Quién sos, bro?' });
  }

  const token = authHeader.slice(6); // quitar "Token " del inicio

  if (!VALID_TOKENS[token]) {
    return res.status(401).json({ error: 'Quién sos, bro?' });
  }

  // Guardamos el nombre del servicio para usarlo después si queremos
  req.serviceName = VALID_TOKENS[token];
  next(); // todo bien, seguir al handler
}

POST /logs — recibir y guardar logs

app.post('/logs', authMiddleware, (req, res) => {
  try {
    // Soportar tanto un solo log como un array de logs
    const logs = Array.isArray(req.body) ? req.body : [req.body];
    const received_at = new Date().toISOString();

    // Validar cada log antes de insertar cualquiera
    const required = ['timestamp', 'service', 'severity', 'message'];
    for (const log of logs) {
      for (const field of required) {
        if (!log[field]) {
          return res.status(400).json({ error: `Campo requerido: ${field}` });
        }
      }
    }

    // Insertar todos en una transacción (más rápido y atómico)
    const insert = db.prepare(`
      INSERT INTO logs (timestamp, service, severity, message, received_at)
      VALUES (@timestamp, @service, @severity, @message, @received_at)
    `);

    const insertMany = db.transaction((items) => {
      for (const log of items) {
        insert.run({ ...log, received_at });
      }
    });

    insertMany(logs);
    res.status(201).json({ message: `${logs.length} log(s) guardado(s)` });

  } catch (err) {
    res.status(500).json({ error: 'Error interno del servidor' });
  }
});

GET /logs — consultar con filtros dinámicos

app.get('/logs', authMiddleware, (req, res) => {
  try {
    const { timestamp_start, timestamp_end,
            received_at_start, received_at_end } = req.query;

    // Construir el WHERE dinámicamente
    const conditions = [];
    const params = {};

    if (timestamp_start) {
      conditions.push('timestamp >= @timestamp_start');
      params.timestamp_start = timestamp_start;
    }
    if (timestamp_end) {
      conditions.push('timestamp <= @timestamp_end');
      params.timestamp_end = timestamp_end;
    }
    if (received_at_start) {
      conditions.push('received_at >= @received_at_start');
      params.received_at_start = received_at_start;
    }
    if (received_at_end) {
      conditions.push('received_at <= @received_at_end');
      params.received_at_end = received_at_end;
    }

    const whereClause = conditions.length > 0
      ? `WHERE ${conditions.join(' AND ')}`
      : '';

    const query = db.prepare(`
      SELECT * FROM logs ${whereClause}
      ORDER BY timestamp DESC
    `);

    const logs = query.all(params);
    res.json(logs);

  } catch (err) {
    res.status(500).json({ error: 'Error interno del servidor' });
  }
});

Cliente simulado

const axios = require('axios');

const SERVER_URL = 'http://localhost:3000';
const TOKEN = 'token_payment_001';

const SEVERITIES = ['DEBUG', 'INFO', 'WARN', 'ERROR'];
const MESSAGES = [
  'Transacción procesada exitosamente',
  'Timeout al conectar con el gateway',
  'Usuario no encontrado en la DB',
  'Retry #3 fallido, abortando operación'
];

async function sendLog() {
  const log = {
    timestamp: new Date().toISOString(),
    service:   'payment-service',
    severity:  SEVERITIES[Math.floor(Math.random() * SEVERITIES.length)],
    message:   MESSAGES[Math.floor(Math.random() * MESSAGES.length)]
  };

  try {
    await axios.post(`${SERVER_URL}/logs`, log, {
      headers: { 'Authorization': `Token ${TOKEN}` }
    });
    console.log(`[payment] Log enviado: ${log.severity} — ${log.message}`);
  } catch (err) {
    console.error('Error enviando log:', err.message);
  }
}

// Enviar un log cada 2 segundos
setInterval(sendLog, 2000);
